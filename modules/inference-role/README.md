# Soroush inference-role module

Creates the IAM role in **your** AWS account that Soroush assumes for customer-managed
inference: Soroush signs its Amazon Bedrock calls with a short-lived session for this role,
so they run in your account, in your region, on your bill.

The module creates two things, and nothing else:

- an IAM role, `soroush-inference-<soroush_account_id>`, whose trust policy admits only
  Soroush's inference principal and only under your Account's External ID;
- one inline policy on that role, granting `bedrock:InvokeModel` on the inference profiles
  and foundation models you list.

It uses the `aws` provider and creates nothing in Soroush. Point Soroush at the role with
the `soroush_inference_configuration` resource of the
[Soroush provider](https://registry.terraform.io/providers/DanaAIhq/soroush/latest/docs).

## Requirements

- **Terraform 1.9 or later.** The `profile_ids` validation reads its list of geography
  prefixes from `inference-role-arns.json`, and a variable validation can refer to it only
  from Terraform 1.9. The Soroush provider itself works on 1.5.
- **The `hashicorp/aws` provider**, 5.0 or later, with credentials for the AWS account the
  role belongs in.
- **The `DanaAIhq/soroush` provider's `soroush_inference_configuration` data source**, which
  supplies three of the inputs: your External ID, Soroush's inference principal ARN, and
  your Soroush Account id. It needs an `admin` API key.

## Usage

```hcl
data "soroush_inference_configuration" "current" {}

module "soroush_inference_role" {
  source = "github.com/DanaAIhq/terraform-provider-soroush//modules/inference-role?ref=v0.2.0"

  external_id             = data.soroush_inference_configuration.current.external_id
  inference_principal_arn = data.soroush_inference_configuration.current.inference_principal_arn
  soroush_account_id      = data.soroush_inference_configuration.current.account_id

  region      = "us-east-1"
  profile_ids = ["us.amazon.nova-micro-v1:0", "us.amazon.nova-2-lite-v1:0"]
}

resource "soroush_inference_configuration" "this" {
  mode               = "customer_hosted"
  role_arn           = module.soroush_inference_role.role_arn
  region             = "us-east-1"
  primary_profile    = "us.amazon.nova-micro-v1:0"
  escalation_profile = "us.amazon.nova-2-lite-v1:0"
}
```

One `terraform apply` does all of it. The data source can be read before any role exists,
because the External ID is generated by Soroush from nothing the role depends on; the
module then creates the role, and the resource names it. The apply fails unless Soroush can
assume the role and invoke every model named.

**Pin the `ref`.** This module writes an IAM policy, and an unpinned source is an IAM policy
that can change between two applies.

The [customer-managed inference guide](https://registry.terraform.io/providers/DanaAIhq/soroush/latest/docs/guides/customer-managed-inference)
covers the whole setup, including the dashboard and CLI paths, verification, what appears
in your CloudTrail, cost, switching back, and troubleshooting.

## Inputs

| Name | Type | Required | Description |
|---|---|:-:|---|
| `external_id` | `string` | yes | The `sts:ExternalId` the trust policy conditions on. Read it from the data source's `external_id`. |
| `inference_principal_arn` | `string` | yes | The one principal the trust policy admits. Read it from the data source's `inference_principal_arn`. |
| `soroush_account_id` | `string` | yes | Your **Soroush** Account id, not an AWS account id. The role is named `soroush-inference-<soroush_account_id>`. Read it from the data source's `account_id`. |
| `region` | `string` | yes | The AWS region inference runs in. Must equal the resource's `region`. |
| `profile_ids` | `list(string)` | yes | Every Bedrock identifier Soroush may invoke: `primary_profile`, `escalation_profile`, and every identifier in a `model_pin`. |
| `customer_account_id` | `string` | no | Your AWS account id. Leave it unset: the module reads it from the caller identity. |

`profile_ids` must be the **union**. An identifier that is pinned but not listed here is an
`AccessDeniedException` on the generation that reaches for it, not a validation error.
Duplicates are folded and order is kept.

`customer_account_id` exists so the module's plan can be rendered without an AWS
credential, for example in an offline CI job. When it is set, the `aws_caller_identity`
data source is not read, and a value that differs from the account the `aws` provider is
pointed at produces a policy that names the wrong account.

## Outputs

| Name | Description |
|---|---|
| `role_arn` | The role Soroush assumes. Pass it to the resource's `role_arn`. |
| `role_name` | `soroush-inference-<soroush_account_id>`. |
| `invocation_resource_arns` | Every ARN the policy grants `bedrock:InvokeModel` on, in policy order. |
| `permission_policy_json` | The inline permission policy, as IAM receives it. |
| `trust_policy_json` | The trust policy, as IAM receives it. |

The two policies are outputs so that what you grant is visible in `terraform plan` on every
change, not only in state.

## What it grants

For the usage example above, in AWS account `111122223333`, the permission policy is:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel"],
      "Resource": [
        "arn:aws:bedrock:us-east-1:111122223333:inference-profile/us.amazon.nova-micro-v1:0",
        "arn:aws:bedrock:us-*::foundation-model/amazon.nova-micro-v1:0",
        "arn:aws:bedrock:us-east-1:111122223333:inference-profile/us.amazon.nova-2-lite-v1:0",
        "arn:aws:bedrock:us-*::foundation-model/amazon.nova-2-lite-v1:0"
      ]
    }
  ]
}
```

- **One action.** Soroush calls Bedrock's `Converse` API without streaming, which
  authorizes as `bedrock:InvokeModel`. The policy grants no streaming, listing, or
  model-customization action: Soroush does not train, fine-tune, or distil models on your
  data, and the missing permission enforces that.
- **Two ARNs per inference profile.** A cross-region inference profile authorizes against
  the inference-profile ARN, which carries your region and account id, and against the
  foundation-model ARN in whichever region the profile routes to, which carries a region
  wildcard and an empty account field. A bare foundation-model id such as
  `amazon.nova-micro-v1:0` contributes one ARN, in your region.
- **Region wildcards by geography prefix:** `us.` → `us-*`, `eu.` → `eu-*`, `apac.` →
  `ap-*` (there is no `apac-` region), `global.` → `*`. They are read from
  `inference-role-arns.json`, which Soroush publishes with the module so that the module and
  the dashboard render the same ARNs. Don't edit it.
- The region field of a foundation-model ARN is the only wildcard in the policy. Model ids
  are always exact.

The trust policy has one statement, one principal, one action, and one condition:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "<inference_principal_arn>" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "<external_id>" } }
    }
  ]
}
```

Keep it that narrow. A second principal hands the role to whoever else matches it. Without
the `sts:ExternalId` condition, another Soroush customer who learned your role ARN could
point Soroush at your role, and Soroush's verification refuses such a role.

## The role name is a constraint

Soroush's inference principal may assume only `arn:aws:iam::*:role/soroush-inference-*`,
so a role named anything else can't be assumed at all. The module sets no IAM path for the
same reason: `role/soroush-inference-*` doesn't match `role/some/path/soroush-inference-x`.

## What it refuses

At plan time, the module refuses:

- an empty or blank `external_id`, or one with leading or trailing whitespace;
- an `inference_principal_arn` that isn't a single IAM role ARN, or that contains a
  wildcard;
- a `soroush_account_id` that is blank, uses characters IAM doesn't allow in a role name,
  or makes the role name longer than 64 characters;
- a `region` that isn't one exact region name;
- an empty `profile_ids`, or an identifier in it that is empty, has surrounding
  whitespace, or is a bare geography such as `eu` or `eu.`.

An identifier whose first segment isn't a geography prefix is accepted as a bare
foundation-model id. Whether your region serves an identifier, and whether your account
has model access, is checked by Soroush's verification, not here.

## Cost, state, and logging

- Customer-hosted inference runs in your account, on your bill. Each verification also
  makes one small model call per distinct identifier, carrying synthetic content and none
  of your documents.
- `external_id` is not marked sensitive, so it is readable in a plan: you need it to write
  the trust policy, and on its own it lets nobody assume the role. Terraform state holds
  it in clear text, so use a remote backend with encryption at rest and restricted access.
- Bedrock model invocation logging is a separate setting in your own account. If you turn
  it on, it writes prompt and completion content to a destination you control.
