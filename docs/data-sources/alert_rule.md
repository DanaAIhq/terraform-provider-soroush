# soroush_alert_rule (Data Source)

Reads an existing Soroush Alert Rule by `id`, so that one workspace can see a rule another manages.

A rule has no name of its own — the platform addresses it by `ruleId` — so `id` is the only lookup key. Every other attribute is read from the platform.

## Example Usage

```terraform
# A complete, runnable root module reading an Alert Rule it does not manage.
#
# An Alert Rule has one lookup route: its platform id. There is no by-name route
# because a rule has no name — the platform identifies it by id alone, and the
# provider does not invent a second identity for it.

terraform {
  required_version = ">= 1.5"

  required_providers {
    soroush = {
      source  = "DanaAIhq/soroush"
      version = "~> 0.1"
    }
  }
}

provider "soroush" {}

data "soroush_alert_rule" "oncall" {
  id = "rul_01HQ8Z0X6ABCDEFGHJKMNPQRS"
}

output "oncall_severity" {
  description = "The severity the rule carries into notifications."
  value       = data.soroush_alert_rule.oncall.severity
}

output "oncall_channels" {
  description = "The notification channel ids the rule notifies."
  value       = data.soroush_alert_rule.oncall.channels
}

output "oncall_selector" {
  description = "Which Checks the rule watches: exactly one of all, logical_names, check_ids."
  value       = data.soroush_alert_rule.oncall.check_selector
}
```

## One lookup route

`id`, and only `id`. A rule has no name on the platform, so there is no by-name
route to offer — the provider does not invent a second identity for it. A lookup
matching nothing fails with a diagnostic naming the id you gave.

## Reading does not claim

`origin` is reported exactly as the platform holds it — `terraform`, `api`, or
`manifest` — and nothing here plans to change it. Reading a manifest-managed rule
leaves it under manifest reconciliation.

## What Terraform state contains for this data source

State records the result like any other: the Project, the selector and therefore
the Check names or ids it lists, the fire-on condition, the severity, the rate
ceiling, the channel ids, the integration names, the consecutive-failure threshold
and grouping key, plus `origin`, `account_id`, and `id`.

It holds no notification **channel configuration** — the addresses, webhook URLs,
and integration credentials behind a channel id are never returned by the API, so
they cannot be recorded. There are no secrets on this data source, and no
attribute carries a `${…}` placeholder.

Use a remote backend with encryption at rest and restricted read access anyway,
and keep the `api_key` in `SOROUSH_API_KEY` rather than in a `provider` block,
where a saved plan file would record it.

### Read-Only

- `account_id` (String) The Account that owns the rule. Determined by the API key, which is bound to exactly one Account.
- `channels` (Set of String) Notification channel ids the rule notifies.
- `check_selector` (Attributes) Which Checks the rule applies to. Exactly one arm is set; the other two are null. (see [below for nested schema](#nestedatt--check_selector))
- `consecutive_failures` (Number) Consecutive failing runs required before the rule fires. Null when the rule does not set one.
- `fire_on` (String) The result condition that fires the rule.
- `grouping_key` (String) The key that groups this rule's alerts into one incident. Null when the rule does not set one.
- `integrations` (Set of String) Third-party paging and incident platforms the rule notifies.
- `max_notification_rate` (Attributes) The ceiling on how often the rule may notify. (see [below for nested schema](#nestedatt--max_notification_rate))
- `origin` (String) Which write path manages the rule: `terraform`, `api`, or `manifest`. Reported as the platform holds it — reading a rule does not claim it.
- `project_id` (String) The Project the rule belongs to.
- `severity` (String) The severity carried into notifications.
